# 大秘境随从生命：Issue #23 验证交接

这是诊断改动，不是放大反馈循环的修复。维护者已确认 `pet_hp_pump` 可能把包含上次秘境倍率的原版重算值当成新基数。观察值到底未放大、还是已经含倍率，仍需原生证据。不要把每个变化值都直接除以上次倍率，否则原版重新算出的干净基数会损失正常生命。

## 收集证据

使用本地合法持有的游戏文件构建本 PR。事件记录不需要环境变量。使用玩家对应的召唤物或束缚恶魔和增益复现，然后分享普通诊断日志。记录召唤技能 / 恶魔种类、实际光环 / 战斗体制；`auto_buff` 是已应用设置，不是该单位实际受到了哪些增益。游戏文件、存档和派生数据表留在本地。

搜索 `pet-life`。每条事件包含秘境序号（`run`，进程内编号）、状态（0 空闲、1 进行中、2 完成）、层数、服务端拍号、单位 ID、宠物类型、类号、模式、单位等级、此前缓存的基数 / 最后写值 / 倍率、观察到的上限 / 当前生命、选定基数、倍率（1000 = ×1）、封顶前目标、写入值和原版即时读回值。生命都是原始 ×256 定点数。`commits` 是存档提交计数，不证明这些特定数值已经落盘。

原因：`new` = 新缓存项，`sidecar` = 类号 / 值命中侧文件，`rebase` = 观察上限不同于上次写值，`scale` / `restore` = 已有缓存且处于放大 / 不放大状态。非正上限单独记为 `invalid`。稳定项不记事件，除非开启已有 `DM_RIFT_TEST_PETDUMP=1` 诊断。

按游戏指针 / 秘境序号 / 状态，额外记录和属性读取最多 64 次，之后只记一次限流提示。完成或放弃刷新额度，使恢复基数仍有日志。原有生命变化日志和可选定时读数不变。即时读回不是两拍之间原版重算的调用追踪；需用本地合法持有的二进制定位真实重算位置，再补该处观测。

## 原生验证矩阵

1. 从干净召唤物开始，记录入场前、首次放大、数次原版增益刷新。比较自动补增益关 / 开、无光环 / 有光环、战斗体制施加 / 到期、换武器、升技能、重新召唤。至少两只同类号单位分别记录。
2. 对照 `observed_max`、`prev_last`、`prev_base`，确定重算使用原始基数还是宿主修改的上限。记录增益前后真实原版属性来源，不要未经证实把有效属性 7 当成未放大基数。
3. 尽可能复现封顶后回到 1。区分非正读数、正数原始值 256（一点生命）、原版算术行为与宿主封顶。宿主乘法已经使用 `long long`；这些记录不证明溢出发生在哪里。
4. 验证完成、放弃、回城、换层、单位死亡 / 重召、换游戏。正常增益应保留，当前生命比例有效，恢复后的上限应与技能和增益相同的干净对照一致。
5. 放大开 / 关分别保存退出再读档，在本地一起核对角色档和 `.dm_pets`。测试同类号多只及重叠存档提交，不能仅凭计数判断持久化成功。

正式修复需要证实的未放大来源，或能区分原版重算干净基数与重算宿主放大值的方法，并回归这两类路径。重复补增益不能累乘秘境倍率，升技能仍应正常生效。保持侧文件兼容及物品 / 角色数据安全。不要因诊断 PR 合并就关闭 #23。

## 宿主检查的范围

`t_rift_pet_trace` 包含生产源码，检查诊断字段、原始精度、封顶标记、恢复记录、限流与重置边界，不调用原版地址。不覆盖宠物表遍历、完整 pump、增益、存档序列化及原版属性实现。严格语法检查覆盖生产 pump。完整构建和原生 / iPad 运行需要当前环境没有的游戏文件。
